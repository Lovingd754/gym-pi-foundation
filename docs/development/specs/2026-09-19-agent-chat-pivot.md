# 对话式健身 Agent 转型决策稿

- 日期：2026-09-19
- 产品语言：简体中文优先
- 运行时：`@earendil-works/pi-agent-core` 0.85.1（经 `FitnessAgentRuntime` 适配层）
- 状态：产品讨论已逐条确认，作为后续实现的约束文件

## 1. 一句话结论

产品主体是一个**对话窗口**。用户和 agent 对话，对话过程中能看到工具调用、记忆确认、方案差异等卡片；计划不是一次性生成的静态文件，而是随对话被查询、微调、重建的活对象。

规则引擎负责算数字，模型负责定策略和组织语言。两者都不能越界。

## 2. 主界面

对话是主窗口，形态对齐 Codex / Claude Code：

- 用户消息 + 助手流式回答（逐字出现，不是等整段）
- 可折叠的工具调用卡片：显示工具名、状态（进行中 / 完成 / 失败），**只显示摘要，不显示原始 JSON**
- 压缩提示：上下文被压缩时，在消息流里插一条浅色提示"较早的对话已压缩为摘要"
- 记忆确认卡片：agent 提议记住某件事时，卡片上给"记住 / 不用记"两个按钮
- 计划差异卡片：agent 提议改方案时，卡片上列出改前改后，需要用户确认才生效
- 运行终止原因：模型轮次保护触发、被用户中止、出错时，要有一句人话说明

计划界面独立保留（今天练什么 / 一周安排 / 开始训练），可以只读，跟随对话改动。

## 3. 分工：模型定策略，规则算数字

| 环节 | 谁负责 | 具体内容 |
| --- | --- | --- |
| 策略 | 模型 | 分化方式、动作取舍、进阶思路、赤字激进度、软约束取舍 |
| 数字 | 规则引擎 | 组数次数、热量、蛋白克数、有氧分钟、就寝时间 |
| 安全 | 规则引擎 | 器械边界、受伤/疾病红线、年龄与人群资格 |
| 表达 | 模型 | 把结构化输出讲成人话，不暴露字段名和内部 id |

模型**不直接产出**公斤数、卡路里、组数这些具体数字，只做选择；所有数字由确定性代码计算并回填。

## 4. 约束模型

- **硬约束**：预定义固定字段，界面里以表单控件呈现（年龄、性别、身高体重、训练年限、每周可训练天数、器械条件、目标等）。它们直接参与规则计算。
- **软约束**：自由文本，因人而异、无法穷举（比如"不喜欢练有氧""膝盖怕深蹲""只能在午休健身"）。交给模型理解，影响它做策略选择；模型判断这类信息是否影响了规则本来会给出的结论。

两条路都要有：结构化表单给规则用，自由文本框给模型用。

## 5. 记忆

agent 提议 → 用户确认 → 才写入。必须支持"这句不用记"。用户可以查看和删除已记住的条目。

不是每轮对话都值得存成记忆：一次性问题不进记忆库。

## 6. Human-in-the-loop 边界

- **改方案**：必须出差异卡片，用户确认后才落库（换动作、改周安排、改目标都算）。
- **只影响某天的临时调整**：直接生效，不用确认（今天睡少了所以少练一组、今天有事把训练挪到明天）。
- **记忆写入**：一律确认。

## 7. 受众与语言

受众是**无严重疾病的普通成年人**，以增肌减脂为主。用户不是专业人士，界面上不能出现专业术语和指标。

术语清洗对照：

| 不要说 | 要说 |
| --- | --- |
| RIR / RPE | 每组留 2 次余力 |
| 减载周 / deload | 轻松周 |
| 超级组 | 两个动作连着做 |
| TDEE / 基础代谢 | 每天大概需要多少热量 |
| 训练容量 / 1RM | 这周总共练几组 / 大概能用多重 |

睡眠不按个人定制，统一给 7–9 小时的标准；只有连续睡不够时，才给两周的过渡安排。

## 8. 饮食表达

不做食物数据库、不做称重，按"配额 + 分配 + 等价替换"来讲：

1. **日总量**（配额）：今天蛋白质 120g、碳水 220g、脂肪 60g、热量 2000kcal。这是当天要凑够的目标。
2. **每餐分配**：把日总量拆到三餐加训练前后，每餐给数字。
3. **具体食物换算**：每个数字后面附等价说法，例如"蛋白质 20g（三个鸡蛋，或一盒 200g 无糖希腊酸奶）"。
4. **一句话说明可调度**：哪一餐没吃够，可以在其他餐补足当天总量。
5. **每餐附"来不及做饭怎么办"**：给便利店/外卖级别的替代选项。

## 9. 三个目标的差异

增肌、减脂、既增肌又减脂，三套东西必须不同：

| 维度 | 增肌 | 减脂 | 同时增肌减脂 |
| --- | --- | --- | --- |
| 热量 | 略高于消耗 | 低于消耗 | 接近消耗，小幅波动 |
| 蛋白质 | 偏高 | 偏高 | 偏高 |
| 力量训练 | 为主，逐步加重 | 为主，维持强度 | 为主，强度优先于总量 |
| 有氧 | 少，作恢复用 | 每天固定时长 | 中等，安排在非训练日 |
| 变化速度 | 每月涨 0.5–1% 体重 | 每周降 0.5–1% 体重 | 体重基本不变，围度变 |

## 10. 对话运行时

- **模型费用我们不设限**。demo 用途，不设费用档位、不设每次对话的用量上限。
- 设置页只保留一个简单的模型选择，列出实际模型名（走 pi 的多模型切换能力）。
- **保留**：工具结果只给摘要；长对话自动压缩。
- 循环保护（轮次上限、超时）只作为防止死循环的兜底，不作为用户可见的额度。

压缩规则：超过阈值时，把较早的往来摘要化并随对话持久化；后续上下文 = 摘要 + 最近若干轮原文；界面上明确提示"上下文已压缩"。

## 11. 多 agent

v1 不做多 agent。单 agent + 确定性校验器足够：模型提策略，校验器拦越界，规则引擎算数字。

## 12. 技术现状盘点

已经具备的：

- `lib/agent/pi-runtime.ts` 是完整的 pi 适配层：Agent 循环、流式 `text-delta`、工具执行、`tool-start` / `tool-end` / `run-end` 事件、中止、超时、调用上限、逐次审计落库。
- `lib/agent/contracts.ts`（运行时接口与事件）、`context.ts`（读最近 20 条）、`limits.ts`、`models.ts`、`system-prompt.ts`、`run-store.ts` 均已就位。
- 数据表 `AgentConversation` / `AgentMessage` / `AgentRun` / `ToolInvocation` 已建好。

还缺的：

- **没有任何地方调用它**。现有的教练对话和周报走的是 `lib/llm` 的单次调用路径，没有工具、没有循环。
- `resolveAgentModel()` 不支持 `LLM_PROVIDER=demo`，没有 key 时 agent 起不来，而本地正是 demo 模式。
- 唯一现有的工具把整份教练数据原样 JSON 吐给模型，与"只给摘要"的约定相反。

对外口径：对开发者诚实说明"基于 pi-agent-core 的 agent 循环"；对用户不作为卖点，产品文案只讲能力。

## 13. 实现顺序

**A. 让循环跑起来（先做）**

- 接上 `FitnessAgentRuntime`，新增流式路由，用户与助手消息落 `AgentMessage`
- 补 demo provider，无 key 也能演示
- 前端渲染文本 + 工具卡片 + 停止原因

**B. 四个工具**

- 读当前计划、读最近训练、读记忆、提议改动（出差异待确认）
- 把现有的训练上下文工具改成摘要输出，并把这个约定固化到工具基类

**C. 记忆**

- 提议 → 确认 → 入库，可查看 / 删除，支持"不用记"

**D. 压缩**

- 超阈值时摘要化较早往来并持久化，上下文 = 摘要 + 最近若干轮

**E. 接入计划生成与记录**

- 录入补硬约束字段与软约束文本框
- 生成走"模型定策略 → 规则算数字 → 预览确认"
- 对话内自然语言记录 + 极简快速记录界面

## 14. 暂不做

- 多 agent
- 进度页可视化
- 独立的周报入口（并入对话）
- 食物数据库与称重
- 模型费用档位与用量上限

已实现的工具：`get_current_plan`（目标、一周安排与每个训练日的动作、有氧、每天饮食总量、睡眠）、`get_recent_training`（最近几次训练、每个动作的最重一组、有氧时长）、`get_memories`（只读已确认的记忆）、`propose_memory`（只创建待确认的提议）。四个工具都只返回一段有字数上限的纯文本，禁止序列化对象——`lib/agent/tools/summary.test.ts` 里有一条会扫描工具目录的护栏测试，出现 `JSON.stringify` 就算失败。

记忆的状态机是两步的：`PENDING` 只有用户能处理，`ACTIVE` 才会进入后续对话的上下文。确认接口在 agent 之外，模型没有路径调用它，所以它不可能把自己猜的东西变成"事实"。用户选"不用记"时，待确认的那条会被直接删除，而不是留在库里。

界面语言：中文现在覆盖了全部命名空间（auth、coach、exercises、history、programs、progress、settings 以及此前的 common、navigation、dashboard、session、fitness、agent），默认语言已改为 `zh-CN`。测试里有两道护栏：一道断言 zh-CN 与 en 的键结构完全一致，另一道断言没有任何命名空间还是英文对象（否则中文界面上会出现英文）。e2e 用例把自己钉在英文上，并单独留了一个用例断言产品默认是中文。

压缩的规则：未折叠的消息超过 30 条时触发，保留最近 12 条原文，更早的折成一段不超过 1200 字的摘要，存在 `AgentConversation.contextSummary` 上，并用 `summarizedThrough` 记住折到哪一条。之后的对话上下文 = 摘要 + 该时间点之后的消息。摘要走一次独立的模型调用（prompt 里带 `COMPACT-CONVERSATION` 标记，demo provider 据它返回脚本摘要）；模型不可用时退回确定性摘要，直接引用用户原话来兜底，绝不编造。压缩在回答交给用户**之后**才跑，并且会单独发一个 `context-compacted` 事件，界面据此提示"较早的对话已压缩"，原文和历史界面完全不受影响。

改方案走的是同一条原则。模型只能提议三种改动：换动作、挪训练日、改每周有氧总量；判定能不能改、改完数字变成多少，全部由 `lib/fitness/plan-change.ts` 的规则做，并且改完必须重新通过 plan schema 校验（改了会破坏不变量的直接拒绝）。提案存在 `AgentPlanProposal` 上，记下它是对哪个方案版本算的；应用时重新跑一次规则并走**和生成方案完全相同的激活路径**（材料化训练计划、旧版本转 SUPERSEDED、新版本 ACTIVE）。所以提案本身永远不是一份方案，模型也没有任何路径自己写上计划。如果提案提出后方案已经被重新生成过，应用会被拒绝并提示重新提问，而不是把改动套到错误的方案上。

模型的输入也做了适配：它说「高脚杯深蹲」这样的中文名也能用，工具会把它映射回 catalog 名再交给规则，否则中文用户每次都必须说英文动作名。

计划生成不再是"规则算完就结束"。评估表单第四步多了一个自由文本框（软约束），内容存进 `FitnessProfile.softConstraints` 并进入计算输入，所以改它会产生新草稿而不是复用旧的。生成流程变成：规则先算出完整方案（和以前完全一样，同步、确定），然后**只在这次新建草稿时**让模型读一遍软约束，回答一个受约束的策略 JSON（避开哪些动作、偏好哪些动作、有氧态度三选一、一句话理由）；策略里不认识的 catalog key 一律丢弃，有氧态度只认三个值；策略再由规则翻译成方案——避开＝换成同类型的替代动作（仍然受器械和能力边界限制），偏好＝调整候选顺序，有氧态度在"最低 20 分钟、最高 150 分钟"的区间内缩放。模型拿不到任何数字，也改不了组数、次数、热量、就寝时间。模型不可用或答非所问时，策略退回中性，方案就退回到原来那份确定性结果——产品在没有模型时依然可用。预览页会把那句理由显示出来（"这份方案是怎么定下来的"）。

变化速度不再用百分比表示。评估里那一栏换成三选一（稳一点／正常／快一点），取值正好是原有安全区间的下沿、中点和上沿，界面把它换算成"大约每月减 X 公斤"说给用户听。这个选择现在**真正驱动热量**：`goalFactorFor(目标, 速度)` 按速度线性换算热量系数并夹住边界（吃少的一侧最多 20% 缺口，吃多的一侧最多 12% 盈余），正常档与改动前的固定系数逐位相同，所以老数据和全部旧测试不受影响。预览页会补一句大白话：「按你选的速度：大约每月减 1.3 公斤，相当于每天比现在少吃约 360 千卡（大概 1.5 碗米饭）」。如果某个速度下热量低到保证不了蛋白质和脂肪下限，规则会拒绝并直接告诉用户"把速度改成稳一点再生成"，而不是给出一份算不通的方案。

对话内记录沿用这个产品里已有的"AI 解析 → 用户确认"模式（原来自练习中的单组解析就是这么做的）。模型只负责把「今天卧推 60 公斤 8 次 3 组」变成一个结构化条目，并且必须先在**用户自己的动作库**里解析出这个动作（同时匹配库里存的名称和界面语言下的显示名，唯一的部分匹配也接受，歧义则拒绝而不是猜）。条目存成待确认提案，用户点「记录」才写入。写入走的是和手动表单同一套 set schema；已有进行中的训练就并进去并保持打开，否则单独建一次自由训练并立即结束，这样它会像普通训练一样出现在历史里。重量按用户自己的单位输入，换算成公斤后存储。

快速记录界面在 `/log`，入口放在对话窗口标题栏（"快速记录"），导航保持五项不变。它只有三步：点动作、确认数字、保存。动作按**最近练过的排前面**（三十个动作按名字排是一张没人滚的列表），重量/次数/组数默认填上次做过的值，保存后数字保留（连续记同一动作是常见情况），下方直接列出今天已记录的内容并且可以逐条删除。写入路径与对话记录**共用同一个函数**，所以"这次记录该落到哪次训练"只有一处答案。
